# コミュニケーション

- 結論から伝え、回答を簡潔にする。
- 定型的な作業手順、ツールの実行、思考過程のすべてを逐一説明しない。
- ユーザーが結果を確認したり、次の行動を判断したりするために役立つ情報だけを報告する。
- 長く構造化されたレポートより、短い段落や少数の箇条書きを優先する。

# コードコメント

- 名前や構造から内容が明らかなコードにはコメントを書かない。
- 将来の保守担当者が、自明ではない制約、リスク、理由を理解する必要がある場合だけコメントを追加する。
- コメントは短くし、コードが「何をしているか」ではなく、なぜその動作が必要なのかを書く。
- 会話の履歴、採用しなかった案、調査の詳細、実装に至るまでの時系列をコメントへ書き写さない。
- 説明コメントを加えるより、コード、命名、構造を明確にすることを優先する。

# Pull Request

- リポジトリに用意されたPull Requestテンプレートに従い、独自形式へ置き換えない。
- 関係する項目を簡潔に記入し、レビューに役立たない任意項目は省略する。
- 実際の変更内容と、レビューに直接必要な情報だけを書く。
- ユーザーから示されていない変更理由、背景、リスク、文脈を推測して補わない。
- リポジトリのテンプレートで明示的に求められていない限り、テストや確認を実施したという定型的な記述を追加しない。
- 作業を時系列で説明したり、変更に至った会話を再現したりしない。
- 実装時の判断をすべて記録しない。レビューの判断に必要な場合や、重要な制約をコードから推測できない場合だけ記載する。
- タイトル、概要、テスト欄、コードコメント、コミットメッセージの間で同じ情報を繰り返さない。
