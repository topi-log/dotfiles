# プロダクトマップの作成と更新

プロダクトマップ `~/.claude/spec-research/products.md` は、調査の出発点になるリポジトリの役割と連携の一覧。dotfiles では管理せず、マシンごとに置く。

## 形式

```markdown
# プロダクトマップ

org: <org>

## 担当範囲

<ユーザーの担当領域。範囲外のリポジトリは質問で求められない限り調べない>

## リポジトリ

| リポジトリ | 呼び名 | 役割 | ローカルパス | ブランチ | 確認済みコミット |
|---|---|---|---|---|---|
| <repo> | <略称、複数可。モノレポ内のものは「名前（`dir/`）」> | <1行> | <~/...> | <デフォルトブランチ> | <短縮ハッシュ> |

## 共有データ

| データ | スキーマを持つリポジトリ | 読み書きするリポジトリ |
|---|---|---|
| <DB 名、Firebase RTDB、S3 バケットなど> | <repo> | <repo（読み/書き）、…> |

## 連携

| 呼ぶ側 | 呼ばれる側 | 手段 | やり取りするもの |
|---|---|---|---|
| <repo> | <repo> | GraphQL / REST / キュー / メール など | <主なデータ・操作> |

## 呼ぶ側だけ確認できた連携

| 呼ぶ側 | 呼び先 | 手段 | 呼ばれる側の候補 |
|---|---|---|---|
| <repo> | <エンドポイントなど> | REST など | <登録外のリポジトリ、Lambda など。不明なら空欄> |
```

共有 DB を介したやり取りは「共有データ」の表にまとめ、「連携」の表には API やキューなど直接の呼び出しを書く。

## 作成

対象のリポジトリはユーザーに指定してもらう。org には他部署のリポジトリも含まれるため、org 全体を一覧して決めない。

あわせて clone の場所と、ユーザーの担当領域（Web、バックエンド、モバイルなど）を聞く。担当範囲外のリポジトリも、連携をたどるために登録はする。親フォルダを指定された場合は、その下の各 clone の `git remote get-url origin` からリポジトリ名を対応付ける。指定されたリポジトリが実在するかを `gh repo view <org>/<repo>` で確かめ、リネーム済みの場合は現在の名前で登録する。指定されたリポジトリの clone が見つからないときは、別のリポジトリに統合されていないか（go.mod や package.json のモジュール名、移動のコミット）を確かめてから、ユーザーに聞く。統合されていれば、統合先の行の呼び名にディレクトリ付きで書く。

各リポジトリについて、remote のデフォルトブランチをブランチ列に記録し、そのブランチを SKILL.md の手順どおり checkout せずに読み、次を調べて埋める。

- 役割: README、ディレクトリ構成、package.json や go.mod から1行で
- 共有データ: 接続先の DB やストレージと、そのスキーマ（migration）を持つリポジトリ
- 連携: 他リポジトリのエンドポイント・GraphQL を参照している箇所

リポジトリが多い場合は、プロダクトのまとまりごとにサブエージェントで並行して調べる。サブエージェントが挙げた連携は、呼ばれる側のルーティングやスキーマを自分で確かめてから表に入れる。呼ばれる側が登録したリポジトリに見つからなければ「呼ぶ側だけ確認できた連携」に入れる。調べたコミットを「確認済みコミット」に記録する。

コミットされた API キーなどの秘密情報を見つけたら、値は書かず、ファイルの場所だけユーザーに伝える。

## 更新

仕様調査で関係するリポジトリについて、確認済みコミットと開発ブランチの最新を比べる。`git fetch` が失敗したときは更新しない。

```bash
git -C <path> fetch origin <branch>
git -C <path> diff --stat <確認済みコミット> origin/<branch>
```

差分のうち、スキーマ・migration、DB の接続先、他リポジトリへのクライアントに当たるファイルが変わっていれば、その部分だけ調べ直して表を直す。変わっていなければ確認済みコミットだけ進める。

調査の途中で分かった呼び名・役割・連携も、その場で追記する。
