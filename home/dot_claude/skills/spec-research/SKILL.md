# 仕様調査

既存システムの「今どう動いているか」をコードから明らかにし、PM・非エンジニアも読めるレポートにまとめる。

仕様書やチケットの記述より、実際のコードを正とする。読み手は報告内容をそのまま意思決定に使うため、コードで確認した事実と推測を混ぜないことが一番重要になる。

調査中はコードを変更しない。

## 1. 問いを確定する

依頼を次のどれか（複数可）に分類し、何が分かれば答えになるかを一文で決める。

| 種類 | 例 | 答えの形 |
|---|---|---|
| 挙動の確認 | 「○○したらどうなる？」「○○が△△に変わる条件は？」 | 条件ごとの結果の表、状態遷移図 |
| 影響範囲 | 「○○を変えたらどこに影響する？」 | 影響箇所の一覧と影響の内容 |
| データの流れ | 「この値はどこから来る？」「入力値に計算が入っている？」 | 入力から保存・表示までの流れ図と、途中の変換 |
| 新機能の事前調査 | 「○○を入れるには？」 | 今ある仕組み、足りないもの、変更が必要な箇所 |
| 他プロダクトとの繋がり | 「○○とどう連携してる？」 | 連携の方向・手段・やり取りするデータ |

対象の画面・API・データが曖昧で、調査の方向が大きく変わる場合だけ、短く1回確認する。同じ名前の項目が複数のリポジトリやテーブルにあるときは、マップの共有データの表で値の元（スキーマを持つ側）を特定し、そちらを主に調べる。それ以外は前提をレポートに書いて進める。

依頼に誰からの質問か（PM、モバイルエンジニア、CS など）が書かれていれば、その人をレポートの読み手にする。質問者が自分の担当領域について既に知っていることは省き、質問者から見えていない部分に絞る。書かれていなければ PM を読み手として書く。

## 2. 対象のリポジトリを決める

プロダクトマップ `~/.claude/spec-research/products.md` を読む。無い場合は、調査の前に [references/product-map.md](references/product-map.md) の「作成」に従って作る。ユーザーに「マップを作って」「リポジトリを登録して」と頼まれたときも同じ手順で作る。

問いに出てくるプロダクト名や略称と、マップの連携の表から、関係するリポジトリをすべて挙げる。値や状態は、画面・API・バッチ・アプリのあいだで受け渡されることが多い。1つのリポジトリだけで答えを出さない。

マップの「担当範囲」の外にあるリポジトリは、質問で求められない限り調べない。値の流れが範囲外に出る場合は、範囲の境目（API の入力、共有 DB のテーブルなど）までを調べ、その先は対象外だったことをレポートの前提に書く。

挙げたリポジトリについて、[references/product-map.md](references/product-map.md) の「更新」に従い、マップが古くなっていないか確かめてから使う。

コードはマップのローカルパスにある clone から、マップに記録したブランチを読む。リポジトリによって develop、development、main と名前が違うため、記録が無ければ `git -C <path> symbolic-ref --short refs/remotes/origin/HEAD` で remote のデフォルトブランチを調べる。ユーザーの作業中のブランチや未コミットの変更に触れないよう、checkout せずに remote のブランチを直接読む。

キーワードの検索は、同梱の `scripts/search.sh` でマップの全リポジトリをまとめて行う。リポジトリごとに grep を繰り返すより速い。

```bash
~/.claude/skills/spec-research/scripts/search.sh [-i] '<正規表現>' [リポジトリ名 ...] [-- '*.go']
git -C "${path}" fetch origin "${branch}"
git -C "${path}" ls-tree -r --name-only "origin/${branch}"
git -C "${path}" show "origin/${branch}:${file}" | nl -ba | sed -n '40,80p'
```

search.sh はテスト・生成コード・ドキュメントを除外して検索する。それらも含めるときは `-a` を付ける。

シェルは zsh のことがある。`"$b:usecase"` の `:u` のように、変数の直後の `:` は zsh の修飾子として解釈される。変数は必ず `${var}` の形で書く。

根拠のコミットは `git -C <path> rev-parse origin/<branch>` で取る。fetch は、まず1つのリポジトリで試す。認証や通信のエラーで失敗した場合は、残りのリポジトリの fetch は試さず、手元にある origin の参照のまま調べてよい。その場合は、読んだコミットの日付をレポートの前提に書き、ユーザーに fetch が失敗したことを伝える。マップが古くなっていないかの確認と更新は行わない。

マップにローカルパスが無いリポジトリは、clone 済みの場所をユーザーに聞く。clone されていなければ、clone してよいか確認する。`gh api` はコードの読み取りに使わない。`gh search code` は使えるが、1分あたり10回程度の制限があり、取りこぼしも多いので、どのリポジトリに関係しそうかの当たりを付ける用途に留める。

コードを読めない状態になったら、待ち続けたり別の手段で迂回したりせず、調査を止める。足りないアクセスと、それまでに分かったことをユーザーに報告する。

同じ機能の実装が複数ある場合（言語違い、旧版と新版など）は、デプロイ設定や CI から実際に動いているものを特定する。選んだ実装と理由はレポートの前提に書く。

## 3. 入口を見つけて端から端まで追う

画面・API・バッチの名前から入口を探し、入力 → API → ドメイン処理 → DB の順で、行きと帰りの両方を追う。途中で止めると「保存はされるが別の処理で上書きされる」のような仕様を見落とす。

- フロントエンド・アプリ: ルーティング、画面、API クライアント（GraphQL のクエリ・ミューテーション）、入力バリデーション
- バックエンド: ルーター登録・GraphQL リゾルバ、middleware（認証・権限）、ドメイン処理、DB アクセス
- バッチ: 起動スケジュール（cron 定義、スケジューラ設定）、対象データの抽出条件、作成・更新・送信の処理
- 定義: migration、DB スキーマ、GraphQL スキーマ、OpenAPI、proto

追いながら、結果を変える条件を拾う。

- 権限・ロール・ログイン状態による分岐
- 状態（status）の遷移と、遷移を起こす処理の一覧
- バリデーションとエラー時の挙動（画面に何が出るか）
- feature flag、環境変数、設定値による違い
- 非同期処理（キュー、バッチ、イベント）や外部 API・メール送信
- リポジトリ間で制約や計算が食い違っている箇所

## 4. 事実と推測を分ける

各結論に、次のどれかを付ける。

- **確認済み**: コードで確認した。根拠のファイルと行を示す。「チェックが無い」「他から呼ばれていない」など、無いことを検索で確かめた場合も含む。そのときは検索した範囲を書く
- **推測**: コードから強く示唆されるが、実行時の値や外部要因に依存する
- **未確認**: 調べきれなかった。誰に・何を確認すれば分かるかを書く

不具合に見える挙動は、コードの挙動を確認済みとして書き、意図した仕様かどうかを未確認事項に回す。レポートの注意点にも挙げる。

連携は、呼ぶ側と呼ばれる側の両方を確認できたものだけを確認済みにする。連携先が見つからなかった場合は、どのリポジトリを何で検索したかを書く。

リポジトリ内の README や設計メモは、どこを読むかの手がかりとして使い、結論はコードで確かめる。コードと食い違っていれば注意点に書く。

起動スケジュールやエンドポイントの定義が、マップに無いインフラのリポジトリ（Terraform など）にある場合は、未確認事項にそのリポジトリ名を書き、マップへの追加をユーザーに提案する。

本番の設定値、DB の実データ、他チームの運用など、コードからは分からないことを埋め合わせない。

## 5. レポートを Artifact で公開する

Artifact ツールの quickstart は `intent: "other"` で呼ぶ。返ってくるデザインの案内は雛形で代えるので読み込まなくてよい。ページは同梱の [assets/report-template.html](assets/report-template.html) を複製し、`{{…}}` を埋めて作る。見た目は雛形で決まっているので、デザインの検討はしない。使わない要素（流れ図、表など）は消す。流れ図や状態遷移図は `<pre class="mermaid">` に mermaid で書く（Artifact が描画するので、ライブラリは読み込まない）。

ページの構成:

1. **結論** — 問いへの答えを3〜5行。専門用語を避け、読み手がそのまま判断に使える言葉で書く
2. **前提** — 質問者、問いの解釈、調査範囲（対象外にした領域）、調べたリポジトリとコミット、対象にした実装
3. **詳細** — 問いの種類に合った形（条件表、流れ図、状態遷移図、影響一覧など）。画面名・機能名で説明し、関数名は補足に留める
4. **注意点** — 仕様として意外な挙動、リポジトリ間の食い違い、リスク
5. **未確認事項** — 確認先と確認内容
6. **根拠（エンジニア向け）** — 折りたたみ。ファイルパスと行番号、該当コードの抜粋。GitHub の該当行へのリンクにする（コミットハッシュ固定）。パスの `[` `]` `(` `)` は `%5B` `%5D` `%28` `%29` に置き換える。行番号は `git grep -n` や `nl` で確かめた値を使い、概算で書かない

流れ図は、関係するコンポーネントが3つ以上あるときに入れる。短い調査なら詳細と注意点はまとめてよい。

チャットには、結論の要約とリンクを返す。ページは非公開で作られるため、質問者に見せるにはページの Share から共有が必要だと一言添える。
