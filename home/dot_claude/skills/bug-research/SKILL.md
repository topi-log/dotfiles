# 不具合調査

報告された不具合が本当にコードの不具合かを確かめ、そうであれば原因・影響範囲・修正方針をまとめる。依頼文で修正まで求められたときは、再現テストと修正まで行う。

報告の中には、報告者の環境だけで起きているもの（キャッシュ、ブラウザ拡張、セキュリティツール、古いアプリのバージョンなど）や、仕様どおりの挙動を不具合と思ったものも含まれる。そのため、原因を探す前に、まず実装から再現性と再現条件を確かめる。

原因を断定できるのは、コードと報告内容（ログ、再現条件）がつながったときだけ。つながらない候補は候補として書く。読み手は報告をもとに顧客対応や修正の優先度を決めるため、確度を正しく伝えることが一番重要になる。

DB と AWS には接続しない。データやログを見る必要があるときは、ユーザーが実行するクエリを書いて渡す（6 を参照）。

## 1. モードを決める

- **調査のみ**: 「調べて」「原因を知りたい」など。コードは変更しない
- **修正まで**: 「直して」「修正まで」など。原因を特定したら、再現テストと修正を行う。commit はしない

どちらか分からなければ調査のみとして進め、最後に修正するか聞く。

## 2. 報告を整理する

報告は、ユーザーが Slack の内容を整えた文章と、そのまま貼られたエラーログで届く。次を抜き出す。分からない項目は空欄のまま進め、未確認事項に回す。

- 症状: 何が起きたか、本来どうなるべきか
- 報告された条件: 画面・操作・ユーザーの種類・データの状態・端末やブラウザ
- 発生時期と頻度: いつから、毎回か一部か、他の人でも起きているか
- 報告者: CS、PM、エンジニアなど。レポートの読み手になる
- ログ: エラーメッセージ、スタックトレース、リクエスト ID、発生時刻

ログに個人情報やトークンが含まれていたら、レポートには伏せて書く。

## 3. 再現性と再現条件を実装から確かめる

対象のリポジトリとコードの読み方は spec-research skill と同じにする（fetch が失敗したときの扱いも同じ）。`~/.claude/skills/spec-research/SKILL.md` の「2. 対象のリポジトリを決める」に従い、プロダクトマップ、`search.sh`、checkout しない読み方を使う。

まず、報告に関係するファイルの最近の変更を `git -C "${path}" log --oneline -20 "origin/${branch}" -- <関係するパス>` で見る。同じ症状を直したコミットがあれば、それが開発ブランチだけにあるか、本番のブランチ（main など）にも入っているかを `git branch -r --contains <commit>` で確かめる。

報告の用語は画面やコードの用語とずれていることがある。画面の文言や i18n の定義で対応を確かめてから追う。

報告された画面・API・バッチから入力 → API → DB の順に処理を追い、報告の症状を起こしうる経路がコードにあるか、あるならどの条件のときかを調べる。結果を次のどれかに判定する。

- **不具合**: 症状を起こす経路があり、それが意図した仕様ではない。再現条件を具体的に書く
- **既知・修正済み**: 同じ症状を直したコミットがある。本番に入っているか、入っているならその前後どちらで起きたかを確かめる
- **仕様どおり**: 症状は意図した挙動として起きる（勘違いの可能性）。根拠のコードと、報告者への説明を書く
- **環境固有の可能性**: コード上は症状を起こす経路が見当たらない。キャッシュ、ブラウザ拡張、セキュリティツール、ネットワーク、古いアプリのバージョンなど、報告者の環境に依存する候補を挙げ、切り分けの手順（シークレットウィンドウ、別端末、別ユーザーで試すなど）を書く
- **判断できない**: データやログを見ないと分からない。必要なクエリを出す（6）

報告どおりの手順ならコードが正しく動く場合も、すぐに環境固有と決めない。次を疑う。

- 操作の順番が報告と違う場合に、通る処理が変わらないか
- 複数のプロダクトや画面が同じデータを更新する処理で、処理の完了タイミングが前後したときの結果（片方の保存より先にもう片方の処理が走る、通信が遅れる、途中で失敗して片方だけ保存されるなど）
- トランザクションの外で複数の保存や外部 API 呼び出しをしている箇所

ログが無い報告では、この時点でユーザーに「報告者以外の環境や別のユーザーで再現できたか」を聞く。答えを待つ間に進められる調査は進める。

不具合でなければ、4〜5 は飛ばしてレポートに進む。

## 4. 原因を特定する

入口は手がかりの強い順に探す。

1. スタックトレースのファイルと行
2. エラーメッセージの文言（`search.sh` で検索）
3. 3 で見つけた症状の経路
4. 発生し始めた時期の前後の変更: `git -C "${path}" log --since=<日付> --oneline "origin/${branch}" -- <関係するパス>`

仮説を立てたら、報告の症状・条件・ログとすべて矛盾しないかを確かめる。一つでも説明できない点が残れば、その仮説は「候補」に留め、別の仮説も探す。

修正の対象になるのは、ユーザーの担当範囲（マップの「担当範囲」）のリポジトリ。原因が範囲外にあると分かったら、そこで止めて、範囲外のどこが原因の候補かをレポートに書く。

## 5. 影響範囲を調べる

- 同じ処理を通る他の画面・API・バッチ
- 影響を受けるユーザーやデータの条件。該当するレコードを数える・抽出するクエリを出す
- いつから起きているか: 原因の行を入れたコミットを `git log -S '<該当コード>'` や `git blame` で特定する。clone に履歴が無ければ（`git rev-parse --is-shallow-repository` が true）、特定できなかったと書く

データの修正が必要な場合は、修正の手順案と SQL を書くだけにする。

## 6. データやログを確認するクエリを出す

DB の状態や本番のログを見ないと判断できないときは、ユーザーが実行するクエリを書く。何を確かめるためのクエリか、結果がどうなら何が言えるかを添える。結果が無いと先に進めない場合は、クエリを渡して結果を貼ってもらう。

- **SQL**: SELECT のみ。必要な列だけを選び、`SELECT *` や個人情報の列の取得は避ける。`LIMIT` を付ける。テーブル名と列名は migration やモデル定義で確かめる
- **CloudWatch Logs Insights**: ロググループ名がコードや設定から分かれば書き、分からなければユーザーに聞く。対象期間と、絞り込みに使う文言（エラーメッセージ、リクエスト ID、ユーザー ID）を入れる

```sql
-- 目的: <確かめたいこと>
SELECT id, status, updated_at FROM <table> WHERE <条件> ORDER BY updated_at DESC LIMIT 50;
```

```
# ロググループ: <名前>　期間: <開始>〜<終了>
fields @timestamp, @message
| filter @message like /<文言>/
| sort @timestamp desc
| limit 100
```

データの更新・削除のクエリは、修正の手順案としてレポートに書くだけで、実行を前提にした形では渡さない。

## 7. 修正する（修正までのモードで、判定が不具合のときのみ）

作業場所はその都度ユーザーに確認する。既定の提案は「開発ブランチから新しいブランチを切る」。ユーザーの未コミットの変更がある clone では、worktree を提案する。

1. 不具合を再現するテストを書き、失敗することを確かめる
2. 原因に対する最小の修正を入れる。周辺のリファクタリングはしない
3. 再現テストと、変更したパッケージの既存テストを通す
4. 変更内容をユーザーに示す。commit はユーザーが行う

テストを書けない箇所（外部サービス依存など）は、確認手順を書いて代える。

## 8. 結果を報告する

結果はチャットで返す。構成は下のページの構成と同じ順にし、各節は短くまとめる。使わない節は省く。結果を待っているクエリがあれば必ず載せる。修正までのモードでは、変更したファイルとテスト結果も添える。

ユーザーに「アーティファクトにして」「レポートにして」など、ページにするよう頼まれたときだけ Artifact で公開する。ページは spec-research の雛形 `~/.claude/skills/spec-research/assets/report-template.html` を複製して作る。作り方（quickstart、mermaid、根拠のリンク）は spec-research の「5. レポートを Artifact で公開する」と同じ。eyebrow は「不具合調査 / <プロダクト名>」にする。

結論の確度は spec-research と同じ「確認済み／推測／未確認」で示す。

ページの構成:

1. **結論** — 3 の判定（不具合／既知・修正済み／仕様どおり／環境固有の可能性／判断できない）と、原因または理由を1〜3行。読み手は報告者
2. **前提** — 報告者、報告内容の要約、調べたリポジトリとコミット
3. **再現性と再現条件** — コードから分かった発生条件。報告の条件との一致・不一致
4. **原因** — どの処理でなぜ起きるか。必要なら流れ図。不具合でなければ、仕様の説明や環境の切り分け手順
5. **影響範囲** — 影響する機能、ユーザー・データの条件、いつから
6. **修正方針** — 案と推奨。修正までのモードでは、行った修正とテスト結果
7. **確認用クエリ** — SQL と CloudWatch Logs Insights のクエリ、目的、結果の読み方
8. **未確認事項** — 報告者や他チームへの質問（再現できたか、操作の順番、発生時刻など）
9. **根拠（エンジニア向け）** — 折りたたみ。ログと該当コードの対応、原因の行を入れたコミット

使わない節は消す。

ページを作ったときは、チャットに結論の要約とリンクを返す。ページは非公開で作られるため、報告者に見せるにはページの Share から共有が必要だと一言添える。
