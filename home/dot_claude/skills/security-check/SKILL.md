# セキュリティチェック

コードを読んで、悪用できるセキュリティ上の問題を見つけて報告する。コードは変更しない。

報告する価値があるのは、「誰が・何をすると・何が起きるか」を具体的に書ける問題だけ。一般論の指摘（「入力値を検証しましょう」など）や、到達できない経路の問題は、読み手の時間を奪い、本当の問題を埋もれさせる。件数より確度を優先する。

実際の環境に攻撃を試すことはしない。コードを読むだけで判断する。

## 1. 対象を決める

- **自分の変更（PR 前）**: 今のブランチの変更。依頼に対象の指定が無く、作業中のブランチに変更があればこれ
- **機能・リポジトリ**: 「○○の API」「このリポジトリ」など、指定された範囲の既存のコード

自分の変更のときは、開発ブランチとの分岐点からの差分と、未コミットの変更を合わせて見る。

```bash
base=$(git merge-base HEAD "origin/${branch}")
git diff "${base}" --stat
git diff "${base}"
```

差分の行だけを見ない。変更された関数の呼び出し元、適用されている middleware、触っているデータのスキーマまで読んで判断する。認可漏れの多くは、変更行ではなく「変更行の周りに無いもの」にある。

機能・リポジトリのときは、リポジトリが1つでも、spec-research skill と同じ読み方をする。`~/.claude/skills/spec-research/SKILL.md` の「2. 対象のリポジトリを決める」に従い、プロダクトマップの clone から、checkout せずに開発ブランチを読む（fetch が失敗したときの扱いも同じ）。検索には `~/.claude/skills/spec-research/scripts/search.sh` を使う。

```bash
search.sh 'Sprintf|Raw\(' <リポジトリ名> -- '*.go'
search.sh 'dangerouslySetInnerHTML' <リポジトリ名> -- 'src/**'
```

## 2. 入口を洗い出す

攻撃者が触れる入口を先に一覧にする。リポジトリ全体のときは、この一覧が棚卸しの土台になる。

- REST のルート登録と、それぞれに掛かっている認証・認可の middleware
- GraphQL のスキーマの Query / Mutation と、リゾルバでの認可
- Webhook、外部から呼ばれる内部 API（API キーや署名で守られているもの）
- バッチが読む外部入力（ファイル、外部 API の応答、キュー）
- フロントエンドで、外部の値を HTML や URL に埋め込む箇所

認証が要らない入口と、ロールによって結果が変わる入口は特に丁寧に見る。フロントエンドのコードやバンドルに埋め込まれた API キーは、誰でも取り出せるので認証とみなさない。そうしたキーだけで守られた API は、未認証で呼べるものとして評価する。

## 3. 観点ごとに確かめる

- **認可**: ログインしているだけで、他人や他組織のデータを ID 指定で読み書きできないか（IDOR）。GraphQL ではリゾルバごと、ネストしたフィールドごとに確かめる。管理者向けの操作が一般ユーザーのロールで呼べないか
- **認証**: 認証を通らないルートが紛れていないか。トークンの検証（署名、期限、発行者）を省いていないか。ログインや二要素認証に回数制限があるか
- **インジェクション**: SQL を文字列連結や `fmt.Sprintf` で組み立てていないか（クエリビルダの生 SQL 部分も含む）。外部の値をコマンドやテンプレートに渡していないか
- **XSS**: `dangerouslySetInnerHTML`、`href` に外部の値（`javascript:` スキーム）、Markdown や HTML のレンダリング
- **秘密情報**: API キーやパスワードのコミット、`NEXT_PUBLIC_` や `VITE_` など、クライアントに配られる環境変数に秘密を入れていないか、ログやエラー応答に秘密や個人情報を出していないか
- **データの出しすぎ**: API や GraphQL の型が、画面で使わない個人情報や内部の値まで返していないか
- **外部へのリクエスト**: 外部の値で組み立てた URL にサーバーからアクセスしていないか（SSRF）。Webhook の署名を検証しているか
- **ファイル**: アップロードの種類・サイズの制限、署名付き URL の対象と期限、パスに外部の値を使っていないか
- **Web の設定**: CORS の許可元、Cookie の `HttpOnly` / `Secure` / `SameSite`、CSRF 対策、本番での GraphQL の introspection やエラーの詳細表示
- **競合**: 残高、回数、状態の更新で、同時に送られたリクエストが二重に処理されないか

秘密情報は、テストや設定例にもコミットされやすいので、`search.sh -a` で除外なしに探す。値が画面やログに出ないよう、必ず `-m` を付けて値を伏せた結果を読む。見つけても値は書かず、ファイルと行だけを書く。

```bash
search.sh -a -m -i '(api_?key|secret|token|password|private_?key)'
search.sh -a -m '.' <リポジトリ名> -- '*.env*' '**/.env*'
```

## 4. 確かめてから報告する

候補を見つけたら、報告する前に次を確かめる。満たさないものは報告しないか、「要確認」として分けて書く。

- その入口に、実際に外部から到達できるか（ルートが登録されているか、middleware が掛かっているか）
- 攻撃者に必要な条件（未ログイン、一般ユーザー、他組織のユーザーなど）
- 別の層（API Gateway、フレームワークの既定動作、DB の制約）で防がれていないか。コードから分からなければ、そう書く

## 5. 結果を報告する

結果はチャットで返す。ユーザーに「アーティファクトにして」「レポートにして」と頼まれたときだけ、spec-research の雛形 `~/.claude/skills/spec-research/assets/report-template.html` でページにする（eyebrow は「セキュリティチェック / <対象>」）。

重大度:

- **高**: 未認証または一般ユーザーが、他人のデータの読み書き、権限の奪取、秘密情報の取得をできる
- **中**: 条件付きで悪用できる、または影響が限られる

攻撃に必要な前提が、メールアドレスや氏名・生年月日のように他人が知り得る情報だけなら、条件付きとみなさず「高」で評価する。推測できない値（ランダムなトークン、本人だけが受け取る URL）が必要なら「中」以下にする。
- **低**: 直接の悪用は難しいが、防御が一枚欠けている

構成:

1. **結論** — 対象、見つかった件数（高・中・低）、すぐ直すべきもの
2. **指摘** — 重大度の高い順。1件ごとに次を書く
   - 場所: ファイルと行
   - 問題: 1〜2行
   - 悪用の流れ: 誰が・何をすると・何が起きるか
   - 修正案: 具体的なコードの方針
3. **要確認** — コードだけでは判断できなかったもの（別の層で防がれている可能性など）と、確かめる方法
4. **見た範囲** — 対象にしたブランチ・コミット、洗い出した入口の数、見なかった観点

問題が見つからなかったときも、見た範囲を書いて「見つからなかった」と報告する。
